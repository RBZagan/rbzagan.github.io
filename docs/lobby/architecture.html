Architecture

The package is developed as a source tree rather than as a place file, and the tree is split four ways. What follows describes the four areas and what each one is for.

The four areas

Area Runs on Holds
Server The server Everything that decides an outcome. This is the only area that holds state the game depends on.
Client Each player's machine Input and display. It reacts; it does not decide.
Shared Both The shapes and constants both sides must agree on, with no secret values among them.
Assets Both Models, meshes, and other 3D content, kept apart from the code that uses it.

Why the split is where it is

The four areas are not a filing convenience. Each is a trust boundary, and the boundary is the reason the layout is worth keeping.

  • Server — a player can ask for something to happen; they cannot assert that it did. Keeping the deciding code in one place is what makes that true by construction rather than by review.
  • Client — a visual effect drawn locally is a prediction. It is allowed and expected, because the alternative is a game that feels laggy, and it grants no authority.
  • Shared — one copy of a shape, so the two sides cannot disagree about what a message means.
  • Assets — kept out of the source areas entirely, so a model import reads in review as an asset change rather than as code.

Why source, not a place

A Roblox place file is a binary with no reviewable history. Committing a source tree instead means every change is a readable difference, every rename is a rename, and a merge conflict is a conflict two people can both read.

The live tree in Studio stays a mirror. That is what makes the rest work: there is exactly one source of truth, and it is on disk.

One way in

The package exposes a single public entry point. Everything a consumer needs is reachable from it, which keeps the package's internal structure free to change without breaking a dependent. Reaching past it is a sign the boundary is in the wrong place, not that the consumer is being demanding.
