How it works

The shape of the package and the reasoning behind it. This page describes behaviour in plain language — it carries no source.

One side decides, the other side suggests

Everything a player does reaches the server as a request, and the server decides what actually happened. The player's machine may draw what looks like a successful action immediately, so the interface feels responsive — but that drawing is a guess, and the server confirms or overrules it independently.

A client never tells the server that something succeeded. It asks for something to be attempted. That is the difference between a game that is hard to cheat and one that is not, and it is the most important property of the package.

Nothing private reaches a player's machine

Some parts of a game are visible to every player, some are visible to none, and some are visible only to the server. The package keeps those three groups physically separate rather than relying on anyone remembering which is which.

  • Server-held — anything that decides an outcome. It never leaves the server.
  • Shared — the shapes both sides must agree on, such as the format of a message. It carries no secret values.
  • Player-held — input and display only. Safe to read, because nothing worth hiding is there.

Checked at the boundary

Every message crossing between a player's machine and the server is checked before it is allowed to change anything — including messages that look obviously legitimate. The check is the server's own, not a restatement of what the client said.

Where a message describes something physical — that a player reached a target, say — the server works that out for itself rather than taking the client's word for it.

Written to be finished, not started over

Types are declared and checked rather than inferred, so a mistake is caught while it is being written rather than while it is being played. Names follow one consistent scheme, and there is exactly one public way in — which is what lets the inside of the package change without breaking anything that depends on it.

ⓘ

For anyone building on this package: the trust boundary described above is a contract, not an implementation detail. A consumer that assumes the server will confirm everything is relying on a guarantee the package is designed to keep.
